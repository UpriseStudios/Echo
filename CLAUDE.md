# Echo

One-tap portrait runner (iOS/Android). Every failed run replays as a ghost that kills the player on contact.

- What and why: [Assets/Docs/Echo — Game Spec.md](Assets/Docs/Echo%20—%20Game%20Spec.md)
- How: [Assets/Docs/Technical Spec.md](Assets/Docs/Technical%20Spec.md) is the source of truth for implementation.
- Engine: Unity **6000.6.4f1**, 2D, URP 2D renderer, Input System, UGUI + TextMeshPro, Newtonsoft JSON.

## Layout (tech spec 2)

```
Assets/Echo/
  Core/            Echo.Core.asmdef          noEngineReferences: true; every game rule
    Sim/ Course/ Ghosts/ Scoring/ Rules/ Achievements/
  Game/            Echo.Game.asmdef          refs Core, Services; renders Core state, feeds input
  Services/        Echo.Services.asmdef      refs Core; Ads/ Iap/ Analytics/ Share/ Mocks/
  Content/Chunks/  chunk JSON (one chunk per file)
  Editor/          Echo.Editor.asmdef        EchoSceneBuilder (menu Echo/Build Scene), chunk validator
  Tests/EditMode/  Echo.Tests.EditMode.asmdef  refs Core, Game (save and driver tests)
  Tests/PlayMode/  Echo.Tests.PlayMode.asmdef  refs Game
```
Namespaces are Echo.Core.*, Echo.Game.* and Echo.Services.*. Course types use `Echo.Core.Courses`, because a namespace called `Course` would clash with the `Course` type. For the same reason, the score formula is `ScoreRules` in `Echo.Core.Scoring`.
Core entry points: Game drives `Rules/RunSimulation` (player, ghosts and recorder, one tick at a time). The death screen uses `Rules/RunRules` (`CanContinue`, `CanBanish`/`Banish`, `Commit`). Everything saved lives in `Rules/Progress`.

## Determinism rules
- Core has no UnityEngine, floats, System.Random, Time.*, DateTime, or code that depends on Dictionary iteration order.
- All sim maths is `int` in sub-units: 1 unit = 1000. Velocity is sub/tick and gravity is sub/tick².
- The sim ticks at exactly 60 Hz. Game drives it from an accumulator, at most 5 ticks per frame.
- Views may interpolate between states but never write sim state.
- `Runner.Step` follows the 10-step order in tech spec 5 exactly. Don't reorder it. The one addition is step 3b, the double jump (chosen by the user): a tap in the air past coyote time spends one of `SimConfig.AirJumps` at `AirJumpVelocity` (~80% height); the ground refills it in step 2. Variable jump (also chosen by the user): `Runner.Step` takes `held`; in step 5, rising with the finger up uses `SimConfig.ReleaseGravity` (60), but only once the jump is `SimConfig.HopHoldTicks` (6) old (`RunnerState.JumpAge`), so every quick tap makes the same hop, about 64% as high, and a held jump is unchanged (device testing: a one-frame lift was not humanly possible, and hop chunks and overtakes had been proved with it). Every search key includes `JumpAge`. `RunSimulation.Step(tap, held)` records release ticks; ghosts replay them (`GhostRecord.ReleaseTicks`, `GhostReplay.Held`). The searches (`ChunkValidator`, `EncounterPlanner`) try three inputs per tick (`JumpInputs`: none, tap and hold, tap and lift); the planner proves overtakes with the single jump, which is conservative and keeps it fast.
- 1-UP (chosen by the user): `RunSimulation` earns a life every `SimConfig.LifeEveryScore` points (holding at most `MaxLives`) and spends it automatically on death through the same recorded revive as Continue, so ghosts replay it. Continue stays a separate, ad-funded revive.
- Randomness comes only from `Xorshift32`, seeded from the course seed. Chunk libraries are sorted by id (ordinal).
- Ghosts are stored as tap ticks, revive ticks and a death tick, never as positions.
- Ghosts are slow-motion echoes (a revision of tech spec 7, chosen by the user): each ghost replays its exact run on its own ¼-speed clock (`SimConfig.GhostClock*`) with a head start. Grave placement (a user revision: graves had no ghost near them): you overtake each ghost at the chunk boundary just before its gravestone (up to `EncounterPlanner.MaxChunksBeforeGrave` back, never before chunk 2), up to 2 at one boundary, with boundaries holding lethal ghosts a chunk apart. Ghosts claim boundaries in `GhostManager.EncounterOrder`: ghosts that have killed you first, most recent killer first, then the rest newest first, so a killer waits at the same spot for a rematch and a Nemesis can form. `EncounterPlanner` proves each overtake (jointly for a shared boundary) at run start; a ghost with no provable boundary near its grave becomes a harmless faint echo timed to fall onto its grave `GhostManager.EchoLeadX` ahead of you (`EchoFairnessTests`, `EchoGhostTests`). A revive (1-UP or Continue) moves the player back, so `GhostManager.HoldBack` holds every ghost's clock back by the same running time and each overtake stays on the floor it was proved on (device testing: overtakes landed in tunnels after a 1-UP). Lockstep ghosts made any ghost that lived past 1 s unbeatable. Rule tests use `SimConfig.WithLockstepGhosts()`.
- Changing chunks or `SimConfig` changes `ContentVersion`. On a mismatch, saved ghosts are discarded.

## Content
- Every chunk must pass `ChunkValidator` (menu Echo/Validate Chunks; also an EditMode test) with the single jump (`SimConfig.WithAirJumps(0)`): the double jump is forgiveness, never required.
- Every proof search (validator, ghost and Copycat planners, test solvers) tries `JumpInputs`: no tap, tap and hold, tap and lift (a hop), and presses only when they make a ground jump (`JumpInputs.Applies`). In the game any press in the air is the air jump, so a mid-air re-press was never a real move; a buffered press is the same as a press on the landing tick. `JumpInputs.Canonical` drops the finger from the search state when it can't matter.
- The contract: standing anywhere within ±0.7 units of the chunk start, the runner can reach standing within ±0.7 units of its end. It's checked at all 11 reachable speeds, every entry position and every mover phase.
- At 1.5× speed a jump spans 5.8 units, so chunks that need two jumps are 12 units long.
- Hop chunks (`t3_hop_*`) put a ceiling at 2.65 units over a short spike: only a short hop fits (a held jump hits the ceiling). They are tier 3, so they arrive at 400 m; `HopChunks_NeedAShortHop` checks each fails with full jumps only. A one-time hint shows at 350 m.
- Placeholder WAVs in `Content/Audio` are generated only when missing, so replace them with real audio under the same names. The cosmetic catalog is rewritten on every scene build.

  - Core (`Core/Daily`): `RunOptions.Daily` runs are scored on distance, at 100% speed, with no Continue, banish, duel, bounty, twist or power-ups (`DailyRules.Check`); earned 1-UPs work. Ghosts are today's leaders (`DailyRules.AsLeader`: `GhostRecord.Leader`, `Name`, run index above `LeaderRunIndexBase`, rank 1 highest) and the player's own failed attempts (`OwnGhostCap` 20, cleared by a new daily best). Leaders claim meeting points first (`GhostManager.EncounterOrder`); passing a leader means going further than its run. Daily runs are settled by the server (`DailyRules.Settle`) and never committed to progress. `ReelPacket` format 2 carries the daily option and each ghost's leader flag and name.

  - Server (`DailyService`): the seed is HMAC(`DAILY_SEED_SALT`, date) (production reads the `_PROD` secrets, `SecretNames`: `DAILY_SEED_SALT_PROD`, `LEADERBOARDS_ADMIN_KEY_PROD`, with no fallback); the leader cache (key `leaders` in the day's item) is rebuilt at most every 5 min from the top 10 and each leader's best run, 12 versions kept; a version is a SHA-256 of the date and every entry (`DailyService.VersionOf`), so an unchanged rebuild keeps its version and different sets never share one; `SubmitDailyRun` checks the rules, the date (5-minute grace after midnight: UGS archives are read-only, since `versionId` on a score write is only a guard, so a grace run is replayed and kept as that day's best and ghosts but ranked on neither board, `BoardClosed`, and the death screen says the board had closed; a user choice), the seed, the leader version and that the ghosts are exactly the ones given (`DailyRules.SameGhosts`), then replays; 1 submission per 2 s. Your own leader ghost is never shown to you. `Server/Config/daily.lb`: desc, keep best, reset 00:00 UTC with archive. The date override is honoured in development only.
  - Client (`EchoGame.Daily.cs`, `DailyLobbyView`): title button with countdown and a dot until today is played; while the lobby loads, the player's character runs and hops on the empty board (a user revision; `MockBackendService.DailyHold` holds it in tests); lobby with the top 10, your best and rank, yesterday's winner; daily death screen (DISTANCE, best today, rank change, "Next: Name · 812 m"); unsent runs wait in `SaveData.Daily.Pending` and are retried until their day ends; one name label, on the next leader ahead of the player (`LeaderLabel.NextAhead`). In the last 5 minutes before 00:00 UTC the lobby and the HUD say "Board closes in m:ss" (`DailyClock`, by the server's clock; the HUD writes into a fixed buffer). Settings has "Dev: daily <date>" in development builds. `ReplayProbe daily` checks the deployed endpoints.
  - Daily monetisation (a user decision; no power-ups in the daily): **Banish your own ghost**: on the daily death screen when one of your own daily ghosts (never a leader) ended the run, a rewarded ad (`AdPlacements.DailyBanish`) banishes it, `DailyRules.BanishesPerDay` (3) a day, recorded by `BanishDailyGhost` (the day's `BanishesUsed`; the ad can't be verified server-side, the cap bounds it); an ad watched whose call failed is kept as a credit. **Watch a run**: tap any run on the lobby board, a rewarded ad (`AdPlacements.WatchRun`, none for your own) then `GetDailyRun` returns that player's best run whole (`BestReel`: taps, the ghosts it faced, the server's result) and it plays through the replay player (`StartExternalReplay`, no clip, Back returns to the lobby). Runs stored before `BestReel` existed answer "not-available".

Changes take a few seconds to reach the server.

## Non-negotiable rules
1. Echo.Core stays engine-free, as above.
2. Gameplay uses no Rigidbody2D, Collider2D or any other Unity physics.
3. No ads during a run, and no interstitials or banners at all. Rewarded ads only, behind `IAdsService`.
4. SDKs (LevelPlay, Unity IAP, Unity Analytics, NativeShare, iOS ATT support) are used only inside `Echo.Services` adapters. Game sees only the interfaces. The editor runs mocks; real services start on device after consent, once `Settings/Resources/EchoServiceConfig.asset` has real keys (in Resources so the game can always load it; the scene build fails if it does not load). Nothing starts before the consent choice.
5. Ask before adding any package the tech spec doesn't name.
6. Build scenes and prefabs from `Assets/Echo/Editor/EchoSceneBuilder.cs` (menu Echo/Build Scene), never by hand.

UNITY_PATH="/c/Program Files/Unity/Hub/Editor/6000.6.4f1/Editor/Unity.exe"
"$UNITY_PATH" -batchmode -nographics -projectPath . -executeMethod Echo.Editor.EchoSceneBuilder.Build -quit -logFile -
